# Marp スライド制作

Markdown を正本とし、公式の `default` テーマで読みやすい発表資料を作る。構成相談だけなら構成案まで、作成・修正の依頼なら原稿と必要な出力の確認まで進める。

## 作成前の確認

- 作業先の `AGENTS.md`、既存資料、Marp 設定を確認する。既存ファイルや生成物を無断で上書きしない。
- テーマ・目的、聴衆の前提知識、発表時間、元資料、保存先、必要な出力形式を依頼文から把握する。作業に必要な不足事項だけ質問し、既に分かる内容を聞き直さない。
- 新規資料は `theme: default`、`size: 16:9`、`paginate: true` を既定にする。ユーザー指定と既存資料の設定を優先し、勝手にテーマを変更しない。
- [執筆ガイド](references/writing-guide.md) を読んでから構成・原稿を作る。

## 制作の進め方

1. 元資料に基づき、聴衆が持ち帰る要点を決める。外部情報は出典と内容を確認し、推測や未確認事項を区別する。
2. 発表時間に合わせて、各スライドの主張と時間配分を考える。構成案を提示し、承認を求められている場合は原稿作成前に待つ。それ以外は依頼された範囲で続ける。
3. Markdown を作成・修正する。章立てを固定せず、目的に応じて導入、全体像、具体例、注意点、まとめなどを選ぶ。
4. 必要な形式を出力し、レンダリング結果を確認する。文字の縮小より、分割・要約・ノートへの移動を優先して直す。
5. 原稿と生成物のパス、実施した確認、残る未確認事項を報告する。

## テーマと記法

新規資料の最小構成は次を使う。外部 CSS の取得や独自テーマの作成は不要。

```markdown
---
marp: true
theme: default
size: 16:9
paginate: true
---

<!-- _class: lead -->
<!-- _paginate: skip -->

# 勉強会タイトル

発表者・日付

---

# 今日持ち帰ってほしいこと

- この発表の要点
```

- 標準の見出し、箇条書き、表、コードフェンス、画像を優先する。表紙や区切りには `default` の `lead` クラスを必要に応じて使う。
- スライド単位の指定には `_class` などのローカルディレクティブを使い、以降のページに意図せず設定を引き継がない。
- 配色・フォント・文字サイズの場当たり的な変更は避ける。独自 HTML / CSS や複雑なカラム構造は、標準記法で表現できない場合だけ検討する。
- 画像は資料ディレクトリの `assets/` などに置き、相対パスで参照する。ユーザーの画像を移動・変更する前に影響を確認する。
- 発表者ノートはスライド内の HTML コメントで記述できる。秘密情報や公開してはいけない内容は、ノートにも記載しない。

## 出力

`marp --version` で CLI の有無を確認する。この dotfiles では Nix 管理の `marp-cli` を使う。未導入なら Nix の設定反映を案内し、npm のグローバルインストールやシステムへの適用を勝手に行わない。

既存のビルド設定があればそれを使う。なければ資料ディレクトリで、必要な形式だけ生成する。指定がなければ Markdown と確認用 HTML を作り、PDF / PPTX は要求がある場合に出力する。

```sh
mkdir -p dist
marp slides.md -o dist/slides.html
marp slides.md --pdf -o dist/slides.pdf
marp slides.md --pptx -o dist/slides.pptx
```

- PDF / PPTX 出力には対応ブラウザーが必要。この dotfiles では既存の Google Chrome を利用できる。検出失敗時はブラウザーの有無と設定を確認し、無断でインストールしない。
- ローカル画像の読み込みを拒否された場合は、参照先が信頼できる資料内のファイルであることを確認してから `--allow-local-files` を必要なコマンドにだけ付ける。
- HTML を `dist/` に出すと相対画像パスの解決先が変わる場合がある。出力 HTML から実際に画像が読み込めることを確認し、必要なら assets の配置や出力先を調整する。
- 通常の PPTX は各ページが画像になる。Google スライド上で本文を個別編集できず、Markdown で修正して再出力する運用であることを伝える。実験的な編集可能 PPTX への切り替えや Google へのアップロードは、依頼なしに行わない。

## 完了前の確認

- 実行した変換が成功しているか、画像・リンクの参照先が正しいか確認する。
- 利用可能なブラウザーや画像確認手段で、全ページの見切れ、重なり、改行、日本語フォント、コードの可読性を確認する。表紙・コード・図表など、異なるレイアウトを見落とさない。
- 見た目の確認手段が使えない場合は、変換成功と目視未確認を区別して報告する。ビルド成功だけで「はみ出しなし」と断定しない。
- 依頼された形式を生成できなかった場合は、原因と未生成の形式を明示する。未確認の動作や見た目を検証済みとしない。
