# スライド執筆ガイド

## 構成

- 最初に「誰が、何を理解して持ち帰るか」を決める。発表者が話したい項目の羅列にしない。
- 1スライドで伝える主張は原則1つ。見出しは、可能なら内容の結論が分かる言葉にする。
- 背景・課題から具体例へ進み、最後に要点を回収する。短い LT では目次や章区切りを無理に入れない。
- デモ、質疑、画面切り替えも時間配分に含める。枚数だけで所要時間を断定しない。
- 元資料を短くする際は、前提条件、例外、トレードオフを落として意味を変えない。

## 文章と情報量

- 箇条書きはまず3〜5項目を目安にする。厳密な上限ではなく、1項目の長さや図とのバランスで判断する。
- 長文・多段の箇条書き・大きな表は、分割や図解を検討する。文字を小さくして詰め込まない。
- 聴衆が知らない用語や略語は初出で説明する。専門用語の言い換えで意味を曖昧にしない。
- 詳細な補足や話す内容は発表者ノートに回す。ただし、結論の理解に必要な前提をノートだけに隠さない。
- 強調は重要箇所に限定し、色だけで意味を区別しない。画像には内容が伝わる代替テキストを付ける。

## コード・図表

- コードには言語名付きのコードフェンスを使う。説明に必要な範囲だけ掲載し、長い行は構造を保って折り返すか短くする。
- 省略したコードと実行可能なサンプルを区別する。省略によって処理や型の意味が変わらないか確認する。
- API キー、トークン、個人データ、内部 URL などを掲載しない。例には架空の値を使い、実測値のように扱わない。
- 図はラベル、矢印、凡例の意味を揃える。コードや構成図は元資料で確認できた事実に基づく。
- 大きな表は比較軸を絞る。単位、計測条件、基準値など、比較に必要な情報を残す。
- Mermaid などは通常の Marp コードフェンスだけで図になると仮定しない。必要なら利用可能な手段で SVG / PNG に変換し、生成結果を確認する。

## 出典と正確さ

- 外部の事実、引用、図表には出典を付ける。該当スライドには短い出典を置き、必要に応じて末尾に URL 一覧をまとめる。
- 数値、バージョン、仕様は元資料と照合する。裏付けのない効果・性能・利用状況を作らない。
- 事実、推測、提案を区別する。確認できない情報は未確認と明記するか、断定を避ける。
- 第三者の画像やコードは、利用条件を確認する。出典を書くだけで転載可能になるとはみなさない。
