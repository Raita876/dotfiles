# tests: 振る舞いの検証

テストの行数ではなく、変更された契約を検証できるかを見る。テストファイルが変わっていなくても対象にする。

- 主要な成功経路、失敗経路、境界値、互換性への影響に対応するテストを探す。
- 期待値が実装をそのまま複製していないか、モックが問題の境界を隠していないか確認する。
- 非同期処理の待ち忘れ、共有状態、時刻・実行順への依存、偽陽性のアサーションを確認する。
- 設定や文書中心の変更では、評価・ビルド・リソース読込など適切な検証方法を提案する。無理に unit test を要求しない。

不足を指摘する場合は、逃している具体的な退行シナリオと、失敗を検出する最小テストの入力・期待結果を書く。「もっとテストが必要」という一般論で終えない。テストは実行せず、静的に確認した範囲と実行検証の必要性を区別する。
