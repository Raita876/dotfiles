# 体系的なデバッグ

**原則: 修正の前に、必ず根本原因を突き止める。症状だけを消す修正は失敗とみなす。**

手順の文言だけを守って中身を飛ばすのは、手順を破るのと同じ。

## 絶対のルール

```
根本原因を調べる前に修正しない
```

フェーズ 1 を終えていないなら、修正を提案してはいけない。

## 使う場面

あらゆる技術的な問題に使う。

- テストの失敗
- 本番のバグ
- 想定外の挙動
- 性能の問題
- ビルドの失敗
- 連携まわりの問題

**特に次のときこそ使う:**
- 急いでいる (急ぐほど当て推量をしたくなる)
- 「ちょっと直せば済む」ように見える
- すでに何度か修正を試した
- 前の修正が効かなかった
- 問題を完全には理解できていない

**次の理由で飛ばさない:**
- 単純そうに見える (単純なバグにも根本原因はある)
- 急いでいる (急ぐと手戻りが確実に増える)
- すぐ直してほしいと言われた (体系的に進めるほうが、闇雲に試すより速い)

## 4 つのフェーズ

各フェーズを終えてから次へ進む。

### フェーズ 1: 根本原因の調査

**修正を試す前に:**

1. **エラーメッセージを丁寧に読む**
   - エラーや警告を読み飛ばさない。答えがそのまま書いてあることが多い
   - スタックトレースを最後まで読む
   - 行番号、ファイルパス、エラーコードを控える

2. **安定して再現させる**
   - 確実に起こせるか。手順は何か。毎回起きるか
   - 再現しないなら、推測せずに情報を集める

3. **最近の変更を確かめる**
   - 原因になりうる変更は何か。`git diff`、最近のコミット
   - 新しい依存関係、設定の変更、環境の違い

4. **複数のコンポーネントにまたがる場合は証拠を集める**

   CI → ビルド → 署名、API → サービス → DB のように層が分かれているときは、修正を提案する前に、境界ごとに診断用の出力を入れる。

   ```
   各コンポーネントの境界で:
     - 入ってくるデータを出力する
     - 出ていくデータを出力する
     - 環境変数や設定が引き継がれているか確かめる
     - 各層の状態を確かめる

   1 回実行して、どこで壊れているかの証拠を集める
   その証拠から、壊れているコンポーネントを特定する
   そのコンポーネントを詳しく調べる
   ```

   例:
   ```bash
   # 層 1: ワークフロー
   echo "=== ワークフローで使える secret ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # 層 2: ビルドスクリプト
   echo "=== ビルドスクリプトの環境変数 ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY あり" || echo "IDENTITY なし"

   # 層 3: 署名スクリプト
   echo "=== キーチェーンの状態 ==="
   security list-keychains
   security find-identity -v

   # 層 4: 実際の署名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   こうすると、どの層で失敗しているか (secret → ワークフロー ✓、ワークフロー → ビルド ✗ など) が分かる。

5. **データの流れをさかのぼる**

   エラーがコールスタックの深いところで起きているときは、[`references/root-cause-tracing.md`](references/root-cause-tracing.md) の手順でさかのぼる。

   要点:
   - おかしな値はどこで生まれたか
   - その値を渡したのは誰か
   - 発生源に着くまでさかのぼる
   - 症状が出た場所ではなく、発生源で直す

### フェーズ 2: パターンの比較

**直す前にパターンを見つける:**

1. **正常に動いている例を探す**: 同じコードベースで、似ていてちゃんと動くコードを探す
2. **参考実装と比べる**: パターンをなぞるなら、参考実装を流し読みせず最後まで読む
3. **違いを洗い出す**: 動くものと壊れているものの違いを、どんなに小さくても全部挙げる。「これは関係ないはず」と決めつけない
4. **依存関係を把握する**: 必要な他のコンポーネント、設定、環境、前提は何か

### フェーズ 3: 仮説と検証

**科学的に進める:**

1. **仮説を 1 つ立てる**: 「X が根本原因だと考える。理由は Y」とはっきり書く。曖昧にしない
2. **最小限で試す**: 仮説を確かめるための最小の変更をする。変数は 1 つずつ変え、複数を同時に直さない
3. **確かめてから進む**: 効いたらフェーズ 4 へ。効かなければ新しい仮説を立てる。修正を上に積み重ねない
4. **分からないときは**: 「X が分からない」と言う。分かったふりをしない。ユーザーに聞くか、さらに調べる

### フェーズ 4: 実装

**症状ではなく根本原因を直す:**

1. **失敗するテストを作る**
   - できるだけ単純な再現にする
   - 可能なら自動テストにする。テストの仕組みが無ければ使い捨てのスクリプトでよい
   - 直す前に必ず用意する

2. **修正を 1 つだけ入れる**
   - 特定した根本原因に対処する
   - 一度に 1 つの変更にする
   - 「ついでの改善」やリファクタリングを混ぜない

3. **修正を確かめる**
   - テストは通るか。他のテストは壊れていないか。問題は本当に解決したか
   - 成功を報告する前に `verification-before-completion` スキルに従う

4. **修正が効かなかったら**
   - 止まって、何回修正を試したか数える
   - 3 回未満なら、新しい情報を持ってフェーズ 1 からやり直す
   - **3 回以上なら、止まって設計を疑う (次の 5)**。設計を話し合わずに 4 回目の修正をしない

5. **3 回以上失敗したら設計を疑う**

   設計に問題があるときの兆候:
   - 直すたびに、別の場所で新しい共有状態・結合・問題が見つかる
   - 直すには大規模なリファクタリングが必要になる
   - 直すたびに、別の場所に新しい症状が出る

   根本から問い直す:
   - このパターンはそもそも妥当か
   - 惰性で続けていないか
   - 症状を直し続けるより、設計を直すべきではないか

   **これ以上修正を試す前に、ユーザーと相談する。** これは仮説の失敗ではなく、設計の誤り。

## 危険信号 (見つけたらフェーズ 1 に戻る)

次のように考えていたら止まる。

- 「とりあえず直して、調査は後で」
- 「X を変えてみて、動くか試そう」
- 「いくつか変えてからテストを回そう」
- 「テストは飛ばして手で確かめよう」
- 「たぶん X が原因だから直そう」
- 「よく分からないけど、これで動くかも」
- 「パターンは X だけど、少し変えて使おう」
- 調べる前に「主な問題はこれです」と修正案を並べている
- データの流れを追う前に解決策を出している
- **すでに 2 回以上試したのに「もう 1 回だけ」**
- **直すたびに、別の場所で新しい問題が見つかる**

## ユーザーからの「やり方が違う」という合図

次のように言われたら、フェーズ 1 に戻る。

- 「それ、本当に起きてる?」: 確かめずに決めつけている
- 「それで〜は分かる?」: 証拠を集めるべきだった
- 「当てずっぽうはやめて」: 理解しないまま修正を出している
- 「もっとよく考えて」: 症状ではなく前提を疑うべき
- 「行き詰まってる?」: 今のやり方が効いていない

## よくある言い訳と現実

| 言い訳 | 現実 |
|---|---|
| 「単純だから手順は要らない」 | 単純なバグにも根本原因がある。単純なら手順もすぐ終わる |
| 「緊急なので手順を踏む暇がない」 | 体系的に進めるほうが、当て推量を繰り返すより速い |
| 「まず試して、それから調べる」 | 最初の修正がその後のやり方を決める。最初から正しく進める |
| 「直ったのを確かめてからテストを書く」 | テストの無い修正は定着しない。先にテストを書けば証明になる |
| 「まとめて直したほうが速い」 | 何が効いたか切り分けられず、新しいバグも生む |
| 「参考実装が長いので適当に合わせる」 | 中途半端な理解は確実にバグを生む。最後まで読む |
| 「問題が見えたので直す」 | 症状が見えたことと、原因が分かったことは違う |
| 「もう 1 回だけ」(2 回以上失敗した後) | 3 回以上の失敗は設計の問題。パターンを疑う |

## 早見表

| フェーズ | やること | 終わる条件 |
|---|---|---|
| 1. 根本原因 | エラーを読む、再現、変更の確認、証拠集め | 何が・なぜ起きているか分かった |
| 2. パターン | 動く例を探して比べる | 違いが分かった |
| 3. 仮説 | 仮説を立て、最小限で試す | 仮説が確かめられたか、新しい仮説を立てた |
| 4. 実装 | テストを作り、直し、確かめる | バグが解決し、テストが通る |

## 「根本原因が無い」と分かったとき

調べた結果、本当に環境・タイミング・外部の要因だった場合:

1. 手順は終わっている
2. 何を調べたかを書き残す
3. 適切な対処 (リトライ、タイムアウト、エラーメッセージ) を入れる
4. 次に調べるときのための監視やログを足す

ただし「根本原因が無い」ケースの 95% は、調査が足りていないだけ。
