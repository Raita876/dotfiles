# リポジトリ調査

実装を根拠に、初めて読む人が主要な責務・依存関係・処理の流れを追える調査レポートを作成する。文書と実装が異なる場合は、その違いを明示する。

## 調査の進め方

- 指定されたリポジトリ・対象機能・調査観点を優先する。指定がなければ全体像を把握し、主要な実行経路を掘り下げる。大規模なリポジトリでは代表的な経路を選び、調査対象と未調査範囲を明記する。
- `AGENTS.md` などのリポジトリ指示、README、ディレクトリ構成、依存関係、ビルド・起動設定から入口を探す。生成物や依存パッケージの全件読み込みを避け、`rg --files` や `rg` で関連箇所を絞る。
- エントリーポイントから呼び出し先を追い、モジュールの責務、内部・外部との境界、永続化、非同期処理を確認する。テストは意図や境界条件の補助資料として使い、テストだけで実装の動作を断定しない。
- データモデルはスキーマ、マイグレーション、ORM 定義、クエリを照合する。設定から分かる構成と、実際に稼働中の構成は区別する。
- API はルート定義、ハンドラー、入出力の型・バリデーション、認証・認可のミドルウェアを追う。OpenAPI、GraphQL スキーマ、Protocol Buffers などの定義があれば実装と照合する。
- 調査に必要な範囲を読む。秘密情報の値や個人データをレポートに転載しない。静的調査を基本とし、コードの変更、依存関係のインストール、サービスの起動、外部システムへのアクセスは調査のために当然必要とはみなさない。

## レポート

日本語を基本に、ユーザー指定の言語・出力先・形式があれば従う。指定がなければ `docs/repository-research.md` に保存する。既存ファイルがあれば内容を確認し、別の調査を失わないよう新しい名前を選ぶか、同じ調査の更新として編集する。

対象に応じて次の内容をまとめる。該当しない項目を埋めるために架空の構成を加えない。

- **概要と調査範囲**: システムの目的、対象ディレクトリ、調査時点のコミット、未コミット差分の有無、未調査範囲。
- **構成と責務**: 主要ディレクトリ、実行単位、使用技術、起動・ビルド・デプロイ設定の入口。
- **アーキテクチャ図**: 内部コンポーネント、外部サービス、データストアと接続関係。
- **主要フロー**: 代表的なユースケースの入口から応答・永続化までの処理とシーケンス図。
- **API 仕様**: 提供する API の一覧と主要な入出力・認証・エラー。Mermaid ではなく Markdown の表とコード例で記載する。
- **データモデル**: 主要エンティティ、キー、関係と ER 図。
- **設定と運用上の境界**: 環境変数の名前と用途、外部依存、認証・認可の境界、エラー処理など、理解に必要な事項。
- **未確認事項**: 静的調査で確定できない挙動、実装と文書の差異、追加調査の入口。

重要な説明と図には、根拠となる相対ファイルパスとシンボル名を添える。行番号を付ける場合は実際のファイルで確認する。レポートから辿れる相対リンクを使い、事実・推測・未確認を区別する。「存在しない」と断定する前に調査範囲を考慮する。

## API 仕様

- HTTP API はメソッド、パス、用途、認証・認可条件を一覧表にする。パス・クエリ・ヘッダー・ボディの各パラメーターについて、名前、型、必須性、制約を示す。
- レスポンスのステータスコード、主要フィールドと型、エラーの条件と形式を記載する。ページネーションや副作用など、利用時に必要な契約もコードで確認できる範囲で説明する。
- GraphQL や RPC などは、その方式に合わせて操作名、入力、出力、認証・認可条件、エラーをまとめる。提供する API と外部 API の呼び出しを区別する。
- リクエスト・レスポンス例は実装に整合する架空の値を使い、例であることを明記する。既存の仕様ファイルへのリンクと実装との差異も記載する。
- 大量の API がある場合は一覧と主要 API の詳細に分け、詳細調査した範囲を明示する。対象に API がない場合はその旨を記載する。

## Mermaid 図

アーキテクチャ図・シーケンス図・ER 図を可能な限り含める。各図は `mermaid` コードフェンスで記述し、図の目的、対象範囲、根拠を本文で補足する。

- **アーキテクチャ図**: `architecture-beta` を使い、`group` で境界、`service` でコンポーネントやデータストアを表す。接続には `api:R --> L:db` のように接続面と方向を指定し、接続の意味は本文で補足する。アイコンは標準の `cloud`、`database`、`disk`、`internet`、`server` を基本とする。単なるディレクトリ一覧を稼働構成として描かない。Mermaid 11.1.0 以降に対応したレンダラーを利用する。
- **シーケンス図**: `sequenceDiagram` を使う。コードで追えた実際の呼び出し順を示し、非同期処理や主要な分岐は必要に応じて `alt`、`opt`、`loop` で示す。関数呼び出しをすべて並べず、責務の境界に注目する。
- **ER 図**: `erDiagram` を使う。確認できたキーとカーディナリティを示す。外部キー制約とアプリケーション上の関係を区別し、不明な関係は推測で結ばない。永続化モデルがなければ、意味のあるドメインの関係を表せる場合だけ論理モデルとして描き、その旨を明記する。
- 対象にデータモデルや実行フローがない場合など、図が不適切なら省略理由を書く。図の数を揃えるために実体や処理を捏造しない。
- 図が複雑になる場合は全体像と機能別に分割し、図と本文で名称を揃える。アーキテクチャ図の ID は単純な英数字にし、表示ラベルは `[API Server]` のように角括弧で指定する。

## 完了前の確認

- 重要な記述・矢印・エンティティの関係をコードの根拠と照合する。
- 相対リンクの参照先、Markdown のコードフェンス、Mermaid の構文を確認する。利用可能なレンダラーがあれば図を検証し、未検証ならその旨を伝える。
- 作成したレポートのパス、調査範囲、残る不明点をユーザーに簡潔に伝える。
