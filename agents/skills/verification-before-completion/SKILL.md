# 完了前の検証

**原則: 主張より先に証拠を出す。**

文言の抜け道を探してこのルールを避けるのは、ルールを破るのと同じ。

## 絶対のルール

```
新しく実行した検証の証拠なしに、完了を主張しない
```

このメッセージの中で検証コマンドを実行していないなら、「通る」とは言えない。

## 主張する前の手順

```
状態を報告したり、うまくいったと言ったりする前に:

1. 特定する: その主張を証明するコマンドは何か
2. 実行する: そのコマンドを省略せず、今あらためて実行する
3. 読む: 出力を最後まで読み、終了コードと失敗の数を確かめる
4. 照らし合わせる: 出力は主張を裏付けているか
   - いいえ: 実際の状態を証拠つきで伝える
   - はい: 主張を証拠つきで伝える
5. ここで初めて主張する

どれかを飛ばしたら、それは検証ではなく推測
```

## よくある失敗

| 主張 | 必要な証拠 | 足りないもの |
|---|---|---|
| テストが通る | テストコマンドの出力で失敗 0 | 前回の実行結果、「通るはず」 |
| lint が通る | linter の出力でエラー 0 | 一部だけの確認、そこからの類推 |
| ビルドが通る | ビルドコマンドが exit 0 | lint が通った、ログが良さそう |
| バグが直った | 元の症状を再現して、起きないこと | コードを変えたので直ったはず |
| 回帰テストが効いている | red → green を確認した | 1 回通った |
| サブエージェントが作業を終えた | diff に変更がある | エージェントの「成功しました」 |
| 要件を満たした | 要件を 1 行ずつ照らしたチェックリスト | テストが通った |

## 危険信号 (見つけたら止まる)

- 「はず」「たぶん」「〜と思われる」を使っている
- 検証の前に「完了しました」「直りました」「うまくいきました」と言いかけている
- 検証せずにコミット・push・PR 作成をしようとしている
- サブエージェントの成功報告をそのまま信じている
- 一部だけの検証で済ませようとしている
- 「今回だけは」と思っている
- **検証を実行していないのに、成功をほのめかす言い方をしている**

## 言い訳と現実

| 言い訳 | 現実 |
|---|---|
| 「もう動くはず」 | 検証を実行する |
| 「自信がある」 | 自信は証拠ではない |
| 「今回だけ」 | 例外は無い |
| 「lint は通った」 | linter はコンパイラではない |
| 「エージェントが成功と言った」 | 自分で確かめる |
| 「一部の確認で十分」 | 一部では何も証明できない |
| 「言い方が違うので当てはまらない」 | 文言ではなく趣旨に従う |

## 具体例

**テスト:**
```
✅ [テストを実行] [34/34 pass を確認] 「テストはすべて通りました」
❌ 「これで通るはずです」「問題なさそうです」
```

**回帰テスト (TDD の red → green):**
```
✅ テストを書く → 実行 (pass) → 修正を戻す → 実行 (必ず fail) → 修正を戻す → 実行 (pass)
❌ 「回帰テストを書きました」(red → green を確認していない)
```

**ビルド:**
```
✅ [ビルドを実行] [exit 0 を確認] 「ビルドは通りました」
❌ 「lint が通りました」(lint はコンパイルを確かめない)
```

**要件:**
```
✅ 計画を読み直す → チェックリストを作る → 1 つずつ確かめる → 足りない点か完了を伝える
❌ 「テストが通ったので完了です」
```

**サブエージェントへの委任:**
```
✅ エージェントが成功を報告 → diff を確認 → 変更を確かめる → 実際の状態を伝える
❌ エージェントの報告をそのまま伝える
```

## 使う場面

**必ず次の前に使う:**
- 完了・成功を伝える、どんな言い方でも
- 作業の状態を肯定的に伝える
- コミット、PR 作成、タスクの完了
- 次のタスクへ進む
- サブエージェントの結果を受け取って報告する

**ルールが及ぶ範囲:**
- 「完了しました」のような決まった言い方
- 言い換えや同じ意味の表現
- 成功をほのめかす表現
- 完了や正しさを示唆するあらゆる伝え方
